# `@managed struct` — 0.9.0 scoping

**Status:** measured, awaiting the architect. No code, no plan.
**Repo measured:** `~/work/TensionScript` at `main` (`90c0d2fe`, the 0.8.1 release).
**Written:** 2026-10-22. Every claim below is a measurement with a `file:line`
citation; the probes are in `/tmp/ms/` and are reproducible from the commands
quoted inline.

---

## 0. The decision this scopes

From the architect, recorded here and not re-litigated:

- **Plain `struct` stays unmanaged permanently.** The 0.9.0 flip planned in the
  0.8.0 scoping is **cancelled**. The TS6385 warning added in 0.8.1 is therefore
  obsolete and is removed in 0.9.0 (§9).
- **`@managed struct` is a new type kind:** GC-owned, C-layout, heap-allocated,
  with a GC header. The host sees the fields pointer, not the object.
- **Three type kinds, none of them changing from 0.8.x:**

| Kind | GC | C layout | Where it lives | Passed to the host as |
|---|---|---|---|---|
| `class` | yes | no | heap, GC trailer/header | a reference (4 bytes) |
| `struct` (`@unmanaged struct`) | no | yes | wherever the author puts it — an arena, a buffer, `heap.alloc` | a pointer the author supplies |
| `@managed struct` | yes | yes | heap, GC-managed | the fields pointer (automatic) |

- **Rust analogy:** `struct Foo` is `&Foo` (borrowed); `@managed struct Foo` is
  `Box<Foo>` with GC. Value types (`@inline struct`, stack, copies) are 1.0 and
  are *not* this feature.
- **Use case:** a guest creates a struct, the GC owns it, and the host receives
  the fields pointer.

## 1. The GC header — measured

### 1.1 `OBJECT_OVERHEAD` is 16 bytes, a compile-time constant

Defined at `std/assembly/rt/common.ts:73`:

```ts
@inline export const OBJECT_OVERHEAD: usize =
  (offsetof<OBJECT>() - BLOCK_OVERHEAD + AL_MASK) & ~AL_MASK;
```

Every term is compile-time: `offsetof<OBJECT>()` is the 0.8.x builtin,
`BLOCK_OVERHEAD` is `offsetof<BLOCK>()` (`common.ts:33`), `AL_MASK` is a literal
15 (`common.ts:8`). The value is folded, not loaded.

Measured from the emitted code rather than from the arithmetic: the compiled
`__new` guards with `i32.const 1073741804` (`/tmp/ms/m-O3.wat`). `BLOCK_MAXSIZE`
is `(1 << 30) - BLOCK_OVERHEAD` = `1073741820` (`common.ts:38`) and
`OBJECT_MAXSIZE = BLOCK_MAXSIZE - OBJECT_OVERHEAD` (`common.ts:76`), so
`1073741820 - 1073741804 = 16`. **`OBJECT_OVERHEAD` = 16.**

The other two overheads, for completeness: `BLOCK_OVERHEAD` = 4 (one `usize`,
`common.ts:29-33`), `TOTAL_OVERHEAD = BLOCK_OVERHEAD + OBJECT_OVERHEAD` = **20**
(`common.ts:79`).

### 1.2 Header layout

`std/assembly/rt/common.ts:44-70` documents it; the class at `:60-69` is the
authority:

```
 reference - 20   BLOCK.mmInfo      (usize; the memory manager's word)
 reference - 16   OBJECT.gcInfo     (u32)
 reference - 12   OBJECT.gcInfo2    (u32)
 reference -  8   OBJECT.rtId       (u32; the class id)
 reference -  4   OBJECT.rtSize     (u32; the payload size)
 reference +  0   first field
```

`__new` confirms both halves — `std/assembly/rt/itcms.ts:260-272`:

```ts
let obj = changetype<Object>(__alloc(OBJECT_OVERHEAD + size) - BLOCK_OVERHEAD);
obj.rtId = id;
obj.rtSize = <u32>size;
...
let ptr = changetype<usize>(obj) + TOTAL_OVERHEAD;
memory.fill(ptr, 0, size);
return ptr;
```

`__new` allocates `OBJECT_OVERHEAD + size` bytes of payload and returns
`obj + TOTAL_OVERHEAD` — i.e. **the reference a guest holds points at the first
field**, and the header occupies the 20 bytes below it.

Measured in emitted code: `class Foo { a: i32; b: f64; }` — `make()` calls
`__new(16, 4)` and stores `i32.store` at offset 0 and `f64.store offset=8`
(`/tmp/ms/m-O3.wat`). No addition appears between the reference and the store.

### 1.3 How the GC traces fields

Per class, generated by the compiler from the declaration; no field types are
needed at runtime.

- `src/compiler.ts:689-690` emits `compileVisitGlobals` / `compileVisitMembers`.
- `compileVisitMembers` (`src/builtins.ts:11162-11237`) builds a `br_table` over
  class ids and, per class, either `return` (pointer-free) or a call to
  `<Class>~visit`.
- `ensureVisitMembersOf` (`src/builtins.ts:11059`) emits that visitor: for every
  field where `property.type.isManaged` it emits
  `__visit(ptr + property.memoryOffset, cookie)` (`:11128-11129`).

Measured, `-O0` (no Binaryen folding), `class Holder { v: i32; s: string; }`:

```wat
(func $gc3/Holder~visit (param $0 i32) (param $1 i32)
  local.get $0
  local.get $1
  call $~lib/object/Object~visit
  local.get $0
  i32.load offset=4        ;; s at memoryOffset 4
  local.get $1
  call $~lib/rt/itcms/__visit
)
```

`class Scalar { a: i32; b: f64; }` gets **no** visitor at all — `grep -c
'Scalar~visit'` = 0 — and its `br_table` case is a bare `return`
(`src/builtins.ts:11178-11181`, `instance.isPointerfree` →
`src/program.ts:4987-5002`).

So: **a pointer-free `@managed struct` is traced as a leaf — skipped, not
walked**, and the collector still knows its size from `rtSize`. That is the
existing behavior for a scalar-only class and it needs no new mechanism.

### 1.4 The class id is read at `reference - 8`

`compileVisitMembers` loads the id with `module.load(4, … ptr - 8 …)`
(`src/builtins.ts:11207-11214`, comment `// rtId is at -8`), and the emitted
`__visit_members` shows the same `i32.const 8; i32.sub; i32.load` before the
`br_table`. **Any `@managed struct` must keep that relation** — reference =
first field, `rtId` at reference − 8.

## 2. `sizeof` / `offsetof` / `managedPtr`

### 2.1 Measured on the closest existing kinds

`class Foo { a: i32 = 0; b: f64 = 0; }` and
`@unmanaged struct UFoo { a: i32 = 0; b: f64 = 0; }` (`/tmp/ms/sz.ts`):

| expression | managed `class` | `@unmanaged struct` |
|---|---|---|
| `sizeof<T>()` | **4** (reference width) | **16** (C size) |
| `offsetof<T>()` (no arg) | **16** | **16** |
| `offsetof<T>("a")` | 0 | 0 |
| `offsetof<T>("b")` | 8 | 8 |

`sizeof` on a managed class returns `type.byteSize` = 4
(`src/builtins.ts:1264-1281`, the managed branch); on an `@unmanaged` class it
returns `classReference.nextMemoryOffset` (the same branch's unmanaged arm).

### 2.2 What `@managed struct` should report, and the arithmetic

The architect's position — `sizeof<@managed struct Foo>` = 16, the fields size,
not 16 + `OBJECT_OVERHEAD` — is the `@unmanaged` answer, and it is implementable
by taking the same `nextMemoryOffset` branch for the new kind. The arithmetic,
against the header in §1.2:

```
                block base            reference (= fields ptr)
                     |                        |
   ... mmInfo | gcInfo | gcInfo2 | rtId | rtSize |  a  |  b  |
      -20      -16       -12       -8     -4       0      8    16
                                                  └── 16 bytes ──┘
                                                      = sizeof / offsetof<T>()
```

- `sizeof<Foo>()` = 16 = bytes from the fields pointer to the end of the last
  field, rounded to the record's alignment (the 0.8.1 rule).
- `offsetof<Foo>("a")` = 0, `("b")` = 8 — **relative to the fields pointer**,
  which is what the host receives.
- `managedPtr` = the fields pointer = the reference. **See §2.3 — this is the
  one place the brief's arithmetic and the runtime disagree.**

### 2.3 The finding: the reference already *is* the fields pointer

The architect's statement is "field bytes at `ptr + OBJECT_OVERHEAD`, host sees
the fields pointer, `managedPtr(foo) = ptr + OBJECT_OVERHEAD`". Measured against
the runtime, that arithmetic does not hold if `ptr` means the reference:

- `__new` returns `obj + TOTAL_OVERHEAD` (`itcms.ts:268`), and the compiler
  stores field 0 at that returned value with no add (measured in §1.2). So
  **reference = fields pointer already**, and the header is at
  `reference - 20 … - 1`.
- Therefore `managedPtr(foo) == foo`, and the offset from the *block base* to the
  fields is `TOTAL_OVERHEAD` (20), not `OBJECT_OVERHEAD` (16).
- Adding 16 to a reference would point 8 bytes into the second field of the
  example record. Nothing in the emitted field access does that
  (`local.get; i32.load`, §3).

Two readings, and the architect has to pick:

- **(A) Reuse the managed-class convention.** Reference = fields pointer, header
  below. `managedPtr(foo)` is the identity; the host already receives the fields
  pointer when it receives the reference; the GC's `rtId` read at `reference - 8`
  keeps working; shadow-stack rooting keeps working. **No new allocation path,
  no new codegen in field access, no change to `__visit_members`.**
- **(B) A header-first convention** (object base = reference, fields at
  `reference + 16`). This needs a distinct `__new` that returns the base rather
  than the fields pointer, a different `rtId` read (`reference + 8`) in
  `__visit_members`, and a different relation in every GC path that computes
  `obj - TOTAL_OVERHEAD` from a reference (`itcms.ts:161, 198, 212, 250, 277,
  296, 298`). It would also make `@managed struct` references incompatible with
  `class` references in every place that treats them uniformly.

Under (B) the field-access *instruction count* is unchanged (the +16 folds into
the load immediate, §3), so cost is not the discriminator — runtime-convention
compatibility is. **Recommendation: (A).** It satisfies the stated intent ("the
host sees the fields pointer, not the object") exactly, with no new machinery.

### 2.4 C# correspondence

| C# | `@managed struct` |
|---|---|
| `Marshal.SizeOf(typeof(Foo))` = fields size | `sizeof<Foo>()` = 16 |
| `Marshal.OffsetOf(typeof(Foo), "b")` = 8 | `offsetof<Foo>("b")` = 8 |
| `GCHandle.AddrOfPinnedObject()` = fields pointer | the reference itself (§2.3) |
| `[StructLayout(Sequential)] class` pinned for the duration of the `DllImport` call | the shadow-stack rooting emitted around a managed argument (§6) |

The correspondence holds only under reading (A): C#'s handle gives the fields
address, and under (A) the reference *is* that address.

## 3. Field-access codegen

### 3.1 Measured

`-O3`, `class Foo { a: i32; b: f64; }`, body `return <f64>f.a + f.b;`
(`/tmp/ms/acc.ts`, inlined into the export wrapper):

```wat
local.get $0
i32.load                 ;; f.a
f64.convert_i32_s
local.get $0
f64.load offset=8        ;; f.b
f64.add
```

`-O3`, the `@unmanaged struct` twin (`sumU`), is the same shape with the same
two instructions per field:

```wat
local.get $0
i32.load
f64.convert_i32_s
local.get $0
f64.load offset=8
f64.add
```

`-O0` (debug), the accessor the call site reaches (`/tmp/ms/acc-O0.wat`):

```wat
(func $acc/Foo#get:a (param $0 i32) (result i32)
  local.get $0
  i32.load
)
```

### 3.2 Per-instruction count

| | field read | field write |
|---|---|---|
| `@unmanaged struct`, `-O3` | **2** (`local.get`; `i32.load offset=N`) | **3** (`local.get`; `local.get`; `i32.store offset=N`) |
| managed `class`, body at `-O3` | **2** (`local.get`; `i32.load offset=N`) | **3** |
| managed `class`, `-O0` | 2 in the accessor (`Foo#get:a`: `local.get`; `i32.load`), plus the call and shadow-stack grounding at the call site | 3 in the accessor (`Foo#set:a`), plus the same call overhead |

The managed path's extra cost is **not in the field access** — it is the
shadow-stack grounding of the reference (`local.get $0; i32.store` into the
shadow stack) and the `__stack_check` call. `@managed struct` inherits exactly
that, because it is a managed reference.

**Under either convention of §2.3 the field access is 2 instructions:** a wasm
load/store carries a static `offset=N` immediate, so `ptr + 16 + 8` compiles to
`i32.load offset=24`, not to an `i32.add`. The convention question is about
where the *reference* points, not about instruction cost.

## 4. Field validity

Each case measured on the closest existing construct; `@managed struct` itself
does not exist, so "valid" below means *the mechanism it would reuse works
today*.

| Field | Verdict | Evidence and reason |
|---|---|---|
| `a: i32` | **valid** — inline, 4 bytes | scalars inline in a record: measured `offsetof<UFoo>("a")` = 0, `("b")` = 8 |
| `b: f64` | **valid** — inline, 8 bytes | same probe |
| `arr: u32[8]` | **BLOCKED** — crashes the compiler | `class M { arr: u32[8] }` + `new M()` → `AssertionError` at `makeZero` (`src/compiler.ts:10688`, the `default: assert(false)` with no `FixedArray` case), reached from `makeFieldInitializationInConstructor` (`:11070`) via `ensureConstructor` (`:9527`). **Not managed-specific:** `@unmanaged struct U { arr: u32[8] }` + `new U()` crashes identically. `T[N]` works today only in the borrowed context (no constructor) — `offsetof`/`sizeof` and `changetype` access. See §4.1. |
| `inner: struct Inner` | **valid** — 4-byte pointer, *not* inline | measured `@unmanaged struct Outer { head: i32; inner: Inner; tail: i32 }` → `inner` at 4, `tail` at 8, size 12; `sizeof<Inner>` = 8. A record-typed field is a reference in this language (the trap `tension-framework/assembly/ogre/wire.ts:455-460` documents). |
| `ref: class Other` | **valid** — 4-byte GC reference, traced | measured `class Holder { v: i32; s: string }` → `Holder~visit` visits `i32.load offset=4` (§1.3) |
| `mref: @managed struct Other` | **valid by construction** — 4-byte GC reference, traced | same mechanism as `ref`; the field's `isManaged` would be true, so `ensureVisitMembersOf` visits it (`src/builtins.ts:11128`) |
| `marr: @managed struct Other[10]` | **INVALID today — needs GC support** | the type parses and lays out (`@unmanaged struct RefArr { head: i32; arr: Other[4] }` → `arr` at 4, size 20; `sizeof<Other[4]>` = 16), **but the field would not be traced**: measured `isManaged<Other[4]>()` = **0**, `isManaged<Other[]>()` = 1. `Type.isManaged` (`src/types.ts:372-379`) is true only for internal references, and a `FixedArray` type is built with `TypeFlags.None` (`src/types.ts:885-889`). Since the visitor filters on `fieldType.isManaged` (`src/builtins.ts:11128`), every referenced object in the array would be invisible to the collector — a use-after-free, not a missing feature. §4.2. |
| `byval: @managed struct Other` (nested by value) | **not expressible** — refused by the grammar, not by a diagnostic | a record-typed field is a 4-byte reference (§`inner` above); there is no inline-nesting syntax, so "a header inside a header" cannot be written. It silently means a reference. |

### 4.1 `T[N]` in a constructed type: the compiler crash, precisely

`makeZero(type)` (`src/compiler.ts:10685-10705`) switches on `TypeKind` and
`default: assert(false)` at `:10688`; `FixedArray` has no case.
`makeFieldInitializationInConstructor` (`:11057-11076`) calls
`makeZero(fieldType)` for any field without an initializer, so **any
construction of a type with a `T[N]` field traps the compiler**, not the
program:

```
AssertionError: assertion failed
  at r.makeZero (src/compiler.ts:10688)
  at r.makeFieldInitializationInConstructor (src/compiler.ts:11070)
  at r.ensureConstructor (src/compiler.ts:9527)
```

`@managed struct` is heap-allocated by definition, so **every** `@managed struct`
with a `T[N]` field hits this. The fix is not a one-line `case`: `makeZero`
returns a single expression for a setter call, while a fixed array needs an
extent-filling store (`memory.fill(ptr + offset, 0, size)`), so field
initialization must gain a fixed-array path rather than a zero constant. That is
a prerequisite piece of work for §4's "arr" cell, and it is **independent of
`@managed struct`** — `@unmanaged struct` + `new` is broken the same way today.

### 4.2 An inline array of GC references is untraceable as things stand

This is the sharpest constraint in the document. A `T[N]` whose element is a GC
reference is representable and correctly sized, but the collector cannot see its
elements:

- `isManaged<Other[4]>()` is **false** (measured, `/tmp/ms/im.ts`);
- `Type.isManaged` (`src/types.ts:372-379`) only consults `isInternalReference`
  and `classReference`;
- `FixedArray` types are constructed with `TypeFlags.None`
  (`src/types.ts:885-889`);
- the visitor generator skips any field whose type is not managed
  (`src/builtins.ts:11128`).

So allowing `marr` without new GC support would compile and run, and would
collect live elements. **Either `Type.isManaged` learns to follow a fixed
array's element type and the visitor emits a per-element loop, or the field kind
is refused by name.** The former is real work in the visitor generator (a loop
of `__visit(base + i*stride)`), the latter is a diagnostic.

## 5. The host boundary

### 5.1 Measured: an `@external` function with a managed parameter receives the reference

`@external("host", "call_managed") declare function callManaged(p: Foo): void;`
with `class Foo` (`/tmp/ms/abi.ts`) emits:

```wat
(func $export:abi/goM (param $0 i32)
  ...
  global.get $~lib/memory/__stack_pointer
  local.get $0
  i32.store                ;; root the reference while the call is in flight
  ...
  local.get $0
  call $abi/callManaged
  ...
)
```

One `local.get $0` into the call, and one shadow-stack store. **No addition, no
`__pin` call.** The import is typed `(param i32)`.

Under reading (A) of §2.3 this is already exactly the required ABI: the value the
host receives is the fields pointer. Under (B) the compiler would have to add
`OBJECT_OVERHEAD` at every managed-struct argument site.

### 5.2 `managedPtr` is not a builtin

`grep -rn "managedPtr\|fieldsPtr" src/ std/assembly/` returns nothing. There is
no such function to call or extend today; the "automatic" behavior of §5.1 is not
a `managedPtr` implementation, it is the absence of an offset.

### 5.3 Automatic vs explicit — the tradeoff

| | automatic (architect's position) | explicit `managedPtr(p)` in the body |
|---|---|---|
| declaration | `declare function call(p: Foo): void` | `declare function call(p: usize): void`, body calls `managedPtr(p)` |
| host sees | the fields pointer | the fields pointer |
| cost | zero if the reference is the fields pointer (§5.1); +1 folded offset under (B) | one builtin call site, folded to a constant |
| type safety | the signature names the record | the signature is a bare `usize`; the record type is lost at the boundary |
| failure mode | a `@managed struct` argument is treated as a reference everywhere, uniformly | a forgotten `managedPtr` passes a reference the host will read as fields — silently right under (A), silently wrong under (B) |

Automatic is the better contract *because* it keeps one meaning for the type
across the boundary. Its cost is entirely determined by §2.3.

### 5.4 What `@abi.transfer("none")` would mean here

Not implemented anywhere in 0.8.x — `grep -rn "abi.transfer" src/` returns
nothing. Semantically: the host borrows the fields pointer for the duration of
the call and **must not retain it**; the guest's GC keeps the object alive across
the call through the shadow-stack rooting measured in §5.1, and nothing
guarantees it survives after return. The distinction from a retaining transfer is
invisible to the compiler today (there is no transfer attribute), so a scoping
that adopts it must also state what the compiler does differently — an
`@abi.transfer("none")` that changes no emitted code is a comment with a
decorator's syntax.

## 6. Interaction with existing features

| Feature | Works with `@managed struct`? | Evidence |
|---|---|---|
| `@abi.alias` on fields | **yes** — same field metadata | aliases attach to the `TypeNode` of a field (`src/ast.ts`, `TypeNode.attributes`), independent of the declaring kind; `abiNameOf<T>` reads `classReference.getMember(...)` (`src/builtins.ts:1385+`), which exists for any class-like element |
| `T[N]` of scalars | **no, today** — compiler crash | §4.1 |
| `T[N]` of GC references | **no** — untraced | §4.2 |
| `COPY_STRUCT(dst, src)` | **should not compile** (architect) — and currently would | `COPY_STRUCT` is `memory.copy(dst, src, offsetof<T>())` (`std/assembly/util/bytes.ts:133-135`). For a managed `T`, `offsetof<T>()` is the fields size and `dst`/`src` would be fields pointers, so it would "work" as a raw byte copy that bypasses GC accounting and the write barrier. A refusal needs the builtin to reject a managed type argument — there is no such check today (`builtins.ts` resolves `offsetof` by kind, and neither `sizeof` nor `offsetof` refuses a managed class). An explicit `copyFrom(other)` method is the right shape, but it implies the guest can *see* a `@managed struct` copy, which is a language feature in its own right. |
| `changetype<Foo>(ptr)` | **yields the reference** | `changetype<T>` on a class type produces a reference to the object at `ptr`; under reading (A) that reference *is* the fields pointer, so `changetype<Foo>(fieldsPtr)` is the exact inverse of passing the fields pointer. Under (B) it would be the header address, and `changetype` would have to add 16 to give the fields view. |

## 7. What this does *not* move

### 7.1 `layout_hash` — no move implied

`layout_hash()` (`~/work/Tension/tension-core/src/session/arena.rs:1030-1104`)
hashes: header geometry (`REGION_COUNT`, `REGION_DESC_SIZE`, offsets, sizes),
the region table, the type catalogue (`TYPES`), field **name + offset** pairs for
the seven host-visible records, and scalar constants (`MODE_*`, `STATE_*`,
`FAULT_*`, record sizes, ring capacities). Every input is a host constant.

Nothing in the fold reads a guest-side type size, so **adding `@managed struct`
moves nothing**. `@managed struct` is a guest-side representation with no
participant on the host side — the host sees a pointer to bytes, exactly as it
does for `struct` today.

### 7.2 No existing managed class changes size

Measured: `sizeof<class Foo>` = 4 before and after any of this (§2.1); the
`@managed struct` size rule is a branch in `builtin_sizeof`
(`src/builtins.ts:1255-1281`), not a change to `Type.byteSize`, which is the same
property the 0.8.0 variant-B work protected (`store`/`load` widths, container
strides, `alignof`). The only codegen change that could touch existing classes is
§4.1's `makeZero`/field-initialization fix — and every construct it would affect
crashes today, so nothing that works now changes.

## 8. Design questions, answered against measurements

1. **Syntax: `@managed struct` (pre-type).** The 0.8.1 parse is
   `case Token.Struct` (`src/parser.ts:380-405`): decorators are already
   collected before the declaration, and the arm merges them with
   `withUnmanaged(decorators, structRange)` (`:390`). A pre-type `@managed`
   therefore needs no parser work beyond recognizing the decorator name — it
   arrives in the same `decorators` list `@unmanaged` does. The post-type form
   introduced in 0.8.0 exists for *field* annotations (`TypeNode.attributes`) and
   has no declaration-level use; using it for a declaration modifier would be a
   second syntax for the same thing.
2. **`OBJECT_OVERHEAD` = 16, compile-time, stable for wasm32** (§1.1). It is
   stable because it is derived from `usize` width (`BLOCK_OVERHEAD` = 4) and
   `AL_MASK` = 15; on wasm64 it would be 20 by the same formula.
3. **Field access: 2 instructions at `-O3`** (`local.get`; `load offset=N`),
   identical to `@unmanaged struct`; `-O0` adds the accessor call and
   shadow-stack grounding (§3).
4. **Field constraints:** scalars and references valid; `T[N]` of scalars
   blocked by §4.1; `T[N]` of references unsafe until §4.2; by-value nesting not
   expressible (§4).
5. **ABI:** automatic is preferred, and under reading (A) it is free (§5).
6. **Interactions:** §6, including the `COPY_STRUCT` refusal that does not exist
   yet.
7. **Version boundary:** 0.9.0, additive. No type changes to `class` or
   `struct`; the only semantic change is the removal of a warning (§9).

## 9. TS6385 removal

The warning is emitted at `src/parser.ts:399-405` for a `struct` declaration with
neither `@unmanaged` nor `@inline`, using the message registered at
`src/diagnosticMessages.json:216` (`6385`). With the flip cancelled, both go:

- delete the `if (!explicitUnmanaged && !hasInlineDecorator(decorators))` block
  and the `this.warning(...)` call (`src/parser.ts:394-405`);
- delete the `6385` entry (`src/diagnosticMessages.json:216`).

Two things must **not** be removed with it: `decl.declaredAsStruct = true`
(`src/parser.ts:393`), which the `@inline` AS100 gate reads
(`src/program.ts:2101-2109`) and which sets the declaration's decorator flags
(`src/program.ts:2123`); and `hasUnmanagedDecorator` (`src/parser.ts:387`), the
merge that makes `struct` mean `@unmanaged`.

CHANGELOG entry for 0.9.0, in the "changed" voice rather than "fixed":

> A plain `struct` no longer warns. 0.8.x warned (TS6385) that `struct` would
> become a managed type at 0.9.0; that change is cancelled — `struct` means
> `@unmanaged struct` permanently, and always will. Code that added
> `@unmanaged` to silence the warning keeps working unchanged.

That is a *warning* semantic change, not a type change: every 0.8.x program
compiles to the same bytes.

## 10. What forces a "no"

1. **The `OBJECT_OVERHEAD` convention (§2.3).** If the architect requires the
   literal header-first arithmetic — fields at `reference + 16` — the feature
   needs a second allocation path and a different `rtId` relation, which breaks
   the uniform treatment of references in `__visit_members`, the shadow stack,
   and every `obj - TOTAL_OVERHEAD` computation in `itcms.ts`
   (`:161, 198, 212, 250, 277, 296, 298`). That is a runtime change with its own
   risk profile, not a type-kind addition. Under reading (A) the requirement is
   already met and the arithmetic in the brief is the thing that changes.
2. **`T[N]` of scalars (§4.1).** Not a design question but a prerequisite: field
   initialization cannot express a fixed array today, for *any* constructed
   type. `@managed struct` is heap-constructed by definition, so without that
   fix every `@managed struct` with an inline array traps the compiler. The
   feature can ship without `T[N]` fields (refused by name), but it cannot
   silently promise them.
3. **`T[N]` of GC references (§4.2).** Untraced elements are a use-after-free.
   Either the visitor learns element-wise tracing or the field kind is refused.
   Not shippable as-is at any cost.
4. **The ABI convention (§5).** Automatic `managedPtr` needs no coordination
   *if* reading (A) holds. Under (B) every host-side declaration that takes a
   `@managed struct` needs the offset applied consistently on both sides, which
   is a protocol decision, not a compiler one.

---

## 11. Recommendation

**Proceed, with two conditions and one correction.**

- **Correction:** `managedPtr` should be the identity, and the header sits below
  the reference (`reference - 20 … - 1`), because that is what `__new` returns
  and what every GC path assumes (§1.2, §2.3). The brief's
  `ptr + OBJECT_OVERHEAD` describes a convention the runtime does not use. If the
  intent is only "the host receives the fields pointer", (A) delivers it today
  with no codegen change at all.
- **Condition 1:** `@managed struct` ships **without** `T[N]` fields, refused by
  name, until field initialization can express a fixed array (§4.1) and the
  visitor can trace element-wise (§4.2). Both are independently valuable —
  `@unmanaged struct` + `new` is broken by the same gap today.
- **Condition 2:** the `COPY_STRUCT` refusal (§6) is added with the type kind,
  not after it; otherwise the new kind silently inherits a raw byte-copy
  primitive that bypasses the write barrier.

With those, the feature is a type-kind addition plus a `sizeof` branch plus a
decorator arm — no runtime change, **no `layout_hash` move**, and every existing
program compiles to the same bytes.

**Not measured, and why:**

- `@managed struct` does not exist, so every "valid" verdict in §4 is a verdict
  about the mechanism it would reuse, not about the feature itself.
- The GC behavior of a `T[N]`-of-references field could not be observed at
  runtime, because no object with a `T[N]` field can be constructed today (§4.1)
  — the compiler traps first. The untraced-element conclusion rests on the
  measured `isManaged<Other[4]>()` = false plus the visitor filter at
  `src/builtins.ts:11128`, which is a static argument, not a runtime trace.
- `@abi.transfer` does not exist in 0.8.x; §5.4 describes intended semantics
  rather than measured behavior.
- No benchmark of `-O0` field access beyond instruction counts; no timing was
  taken.
- The `layout_hash` claim is a reading of `arena.rs:1030-1104` plus the fact that
  the fold has no guest-type input; the hash was not re-run, because no code
  changed — `tension-core layout-hash` still reports `786288195` on the current
  tree.
