# The async core loop — footprint

> **Status: design.** Nothing here is implemented. This page is the blueprint the
> implementation rounds are briefed from, and the record of the decisions it rests on.
>
> Replaces the role of Backend A (the state-machine lowering) as the *target*. Backend A
> stays as the reference implementation the contract is validated against; it is no longer
> what async is supposed to become.

## 1. What is wrong today, stated once

`await` in Backend A pauses **data**, not **control**.

A lowered `async function` becomes a state struct with a `resumePoint`, plus a `$resume`
function that keeps the body's *structure* and guards every construct on `resumePoint`.
Resuming means re-entering `$resume` at the top and walking until the right point. That is
O(depth) per wake, and it only works for control flow the transform knows how to guard.

The user's objection, which is correct: *"it means every await will poll, this is not real
pause."*

Consequences that follow, all measured or read from the tree:

- **The caller's frame is reused.** `async f()` marks `f`, and `f`'s body ends up as a
  state machine on the caller's stack.
- **Every async function pays**, including ones that never await.
- **`spawn` does not exist.** `spawn` appears only as a marker string in `src/lazy/lower.ts`.
- **Guest-to-guest awaits use a mailbox.** `TaskRecord{class_, key, payload}` is a message,
  and `waiters: Map<TaskRecord, Array<TaskState>>` is the rendezvous.
- **Nothing has ever really blocked.** Every await in Tension today is satisfied by the host
  (`rt.frame()`, `rt.job()`). No await waits on a device. The compromise has never been
  stressed, which is why it has survived this long.

What is **not** wrong: the host-contract path. A wait whose liveness is not the guest's can
only end when the host says so, so unwinding to the host boundary is honest there.
`scheduler.rs`'s park tables, `take_early`, and §5's contract properties all stand.

## 2. The rule this design turns on

**A guest wait needs a stack. A host wait needs a table.**

There are exactly two terminal waits:

| kind | pauses? | liveness owned by | state lives in | resumed by |
|---|---|---|---|---|
| host contract | yes | the host | host tables keyed `(family, key)` | a host call |
| guest continuation | yes | a guest stack | the stack itself | a stack switch |
| guest task | **chains** | → its terminal | — | composition |
| no await | no | — | nothing | nothing |

A guest-task await is **not** a third terminal. `await b()` where `b` suspends is parked on
`b`'s own wait; the waiter list is a callback, not a wake source. Only the two rows above
are terminal.

This is decidable per await at compile time, which is what makes the rest possible.

## 3. The core loop

`__asynccoreloop` is generated by the compiler and present in every program that contains an
await. It is a **core feature**, not a flag — the same footing as `Array` or `String`.
It is emitted because the program used async, not because anyone opted in.

### 3.1 Who runs what

```
__start  (host stack)
  ├─ cont.new $__coreloop        → coreCont
  ├─ cont.new $main              → mainCont      ;; main is NOT called
  └─ resume $coreCont (mainCont) (on $idle → return) (on $done → return)

__coreloop(mainCont)
  loop:
    resume $cur (on $await → park) → finished normally? → $done / next
    park: store the captured continuation, pick the next runnable
```

`cont.new $main` creates main's stack **without executing a single instruction**. Main is
never called — it is resumed. That is why `main` needs no `async` marker and no signature
change: the compiler rewrites `__start`, and nothing else.

**The initial state is: coreloop running, main in hand, not yet started.**

### 3.2 Why coreloop parks only when idle

`resume` is a **call that returns** when the continuation suspends:

```
coreloop:  resume main ─────────────────────────►  main runs
                                                      ... await
           ◄──────────────── returns a continuation ── main suspends
           store it, pick next, resume again
```

So the switch is nesting, not preemption, and coreloop's own state stays on its own stack
where it belongs. Coreloop parks exactly once — when nothing is runnable:

```
coreloop: nothing runnable
  suspend $idle ───────────────────────►  handler returns to __start
                                          __start returns to host
                                          host blocks on epoll / frame tick
                                          host calls __asyncPump()
    ◄──────────────── resume coreCont ──── __asyncPump resumes coreloop
```

Three participants, three parking rules:

| | parks on | how often |
|---|---|---|
| main | every await | every suspension |
| coreloop | `$idle` | only when nothing runnable |
| host | epoll / frame tick | only when coreloop is idle |

### 3.3 The tag vocabulary

```
tag $await  : (cont) → void      ;; guest: "I am waiting on this; here is my stack"
tag $idle   : () → void          ;; coreloop: "nothing runnable; the host owns time now"
tag $done   : (i32) → void       ;; coreloop: "the program finished with this status"
```

`$await` carries the continuation being awaited. `$idle` carries nothing and is the only
path out to the host. `$done` ends the program.

### 3.4 Shape, not exact syntax

```wat
(func $__coreloop (param $main (ref null $ct_any))
  (local $cur (ref null $ct_any))
  (local.set $cur (local.get $main))
  (loop $again
    (block $parked
      (resume $ct_any (on $await $parked) (local.get $cur))
      ;; returned normally: that continuation finished
      (br $again)                      ;; pick the next runnable, or fall to $done
    )
    ;; $parked: the handler received (next-cont, awaited-cont)
    ;;   - if it awaits a host key: add $cur to the wait table
    ;;   - select the next runnable continuation
    (br_if $again (i32.eqz (is-empty)))
    (suspend $idle)
    (br $again)
  )
)
```

The exact `resume`/handler encoding is settled in the spike (§7), not here. This is the
control shape; the syntax is wasmfx's to get right.

## 4. Semantics the user fixed

These are binding decisions from the design conversation, not options.

### 4.1 An async call does not run

```ts
let sumtask = asyncsum(1, 2);   // enqueue only — nothing has executed
blabla();                        // runs normally
let sumres = await sumtask;      // *now* it runs
```

Calling a may-suspend function creates a continuation and its arguments. **No instruction of
the body executes.** This is Python's coroutine model carried one step further: the call is
not even a generator object, it is a suspended stack.

The consequence is deliberate: **nothing happens behind your back.** `asyncsum(1,2)` and
`blabla()` cannot overlap, and that is a property, not a gap.

### 4.2 `spawn(f)`, never `spawn(f())`

`spawn(f())` is structurally impossible in a stackful model, and the reason is evaluation
order: `f()` would begin executing on the **caller's** stack, so by the time `spawn` ran,
part of `f`'s body would already have run on a stack `f` does not own. Then `f`'s first
suspension would capture the caller's stack, cut at a point inside a callee.

The body must run on its own stack from instruction zero, so `spawn` takes the function and
its arguments separately:

```
spawn(f, a, b)   →  new continuation of $f, args stashed, pushed to ready
```

### 4.3 Only awaited work runs

A queued-but-never-awaited call never executes. No orphan work, no surprise side effects,
one word (`spawn`) for "run this independently".

### 4.4 A may-suspend function with no await is free

If the body contains no await, the compiler does not build a continuation, does not queue,
and does not allocate a Task. `async` means "**may** suspend", so a body that cannot suspend
costs nothing.

### 4.5 The root cannot await

The stack that hosts the loop cannot be captured by it. `__coreloop` never awaits; it only
resumes and parks to the host. This is the RTOS rule that the scheduler never blocks, and it
is a structural consequence, not a restriction to work around.

### 4.6 Cooperative, not preemptive

There is no involuntary switch. A task that computes for 500 ms blocks every other task.
The epoch/watchdog can interrupt, but that is a **trap, not a context switch** — it kills,
it does not park.

This is the same trade the tree already records for the process world: *"a root guest that
loops forever freezes this process until SIGINT … the guest owns its loop."*

### 4.7 Nested pump is a named refusal

If a resumed context calls something that itself needs to drain, coreloop would re-enter
itself: two loops, one ready list, corruption. This must be refused **by name** — a
compile-time rule if the call graph allows it, a runtime `coreloopActive` guard otherwise.
Cheap either way; it must exist.

## 5. What the compiler emits

Per program:

- **The tags** `$await`, `$idle`, `$done`.
- **`__coreloop`** — one function, fixed shape, varying only in its ready-queue type.
- **`__start`** rewritten — `cont.new` both, resume coreloop.
- **`__asyncPump`** exported — the single host entry (§6).

Per async function:

- **The entry** — `cont.new $f` plus an argument stash. No state struct, no lifted locals,
  no `resumePoint`, no discriminator ranges.
- **Await sites** — `suspend $await` with the awaited continuation.

Per function that awaits: **nothing**. Depth is free. `main → a() → b() → await` captures one
continuation, not three.

### 5.1 What survives from Backend A

- **`TaskRecord`** — kept, but only for **host contracts**, where a completion arrives from
  outside and has nowhere else to put its payload. Guest-to-guest awaits stop using it: the
  value rides the continuation (suspend passes out, handler return passes in).
- **`scheduler.rs`**'s park tables, `take_early`, `ParkRefusal`, the per-class capacities —
  all stand. They are the host-contract half and they are correct.
- **`scheduler-contract.md` §5** (contract properties: coalescing, one-shot, terminality) —
  stands, and becomes the thing whose type-ification would let the compiler *choose* the
  wait mechanism per await instead of the runtime discovering it.

### 5.2 What is deleted

- `src/async/lower.ts`'s state-machine construction — the state struct, `resumePoint`
  guards, lifted locals, the `$awaited<K>` records.
- `__taskResume` / `__taskWake` / `__taskFail` as *guest* entry points, replaced by
  `__asyncPump` (§6). They may remain internally, called by coreloop.
- The `waiters` map, for guest awaits.

## 6. The host boundary

One export replaces three:

```
__asyncPump(): i32     ;; resume coreloop; returns the number of contexts run
```

The host's whole job:

```
loop {
  if coreloop idle { block on epoll / frame tick }
  write completions into the arena
  __asyncPump()
}
```

That is a clock and an inbox. Compare with today's host loop, which chunks wake batches,
writes three parallel arrays into arena scratch, and calls `__taskResume` per chunk — because
the guest cannot dispatch for itself.

## 7. The emission mechanism — settled by spike (2026-11-18)

Binaryen 131's public JS API has **no continuation constructors**, confirmed:

```
Object.keys(b).filter(k => /^_Binaryen(ContNew|Suspend|Resume|ResumeThrow|StackSwitch)$/.test(k))
→ []
```

`_BinaryenContNewId`, `_BinaryenSuspendId`, `_BinaryenResumeId` exist but are expression **ID
accessors**, not constructors, and are not declared in `src/binaryen-c.h` at all. Upstream's C++
side has the builders (`wasm-builder.h`: `makeContNew`, `makeResume`, `makeSuspend`); the C API —
and therefore the JS API, which is the C API through emscripten — exposes none of them. So
JavaScript cannot *construct* a `cont.new` expression.

**But Binaryen can emit, validate and run a continuation module through the text path.** Measured
end-to-end on snowarch, wasmtime 50.0.1:

```
parseText → setFeatures(GC | StackSwitching | ExceptionHandling | ReferenceTypes)
          → emitBinary → wasm-tools validate --features all  → OK
          → wasmtime: compiles, runs, parks, resumes, returns 1
```

### 7.1 The landmine: GC must be enabled

This is the finding that produced two wrong conclusions on the first pass, so it is written as a
rule rather than a caveat:

**A module containing continuation types must be written with `GC` enabled**, even though stack
switching is the proposal it uses. `HeapType::asWrittenGivenFeatures` (`src/wasm-type.h:280`):

```cpp
// Without GC, only top types like func and extern are supported.
if (!feats.hasGC() && *this != HeapType::string) {
  return getTop();
}
```

Without GC, every concrete heap type is generalized to its top before writing: a continuation of
`(func)` becomes `cont func`, encoded `5d 70` — the *pre-final* form, which wasmtime rejects at parse
with `invalid continuation type`. With GC, the signature survives as a type index and the writer
emits `5d 00`. Same source, four masks, measured:

| feature mask | type section | `wasm-tools validate` |
| --- | --- | --- |
| StackSwitching | `... 5d 70 ...` | invalid continuation type |
| + ReferenceTypes | `... 5d 70 ...` | invalid continuation type |
| + ExceptionHandling | `... 5d 70 ...` | invalid continuation type |
| + **GC** | `... 5d 00 ...` | valid — and runs |

The second half of the landmine: **`_BinaryenModuleSetFeatures(module.ref, mask)` silently does
nothing.** `module.setFeatures(mask)` is the call that applies. A spike using the former reads
`5d 70` back, concludes Binaryen cannot express typed continuations, and is wrong — as this one
briefly was. Anything that emits a continuation module must assert `getFeatures()` afterwards, or
better, assert the emitted type section.

There is no conflict with the tree's position on GC: wasm GC is already a hard dependency of this
fork (the GC arc, `d96ac606`). Async simply makes the compiler *state* it.

### 7.2 The three options, re-ranked

- **(A) Extend our own glue.** Still an emscripten rebuild — but for a **narrower** reason than the
  first pass assumed: the writer is sound, so this is only about exposing constructors
  (`BinaryenContNew`/`Resume`/`Suspend` over the existing C++ builders). Buys programmatic IR,
  optimisation and DWARF. Highest value, highest build cost, no longer "necessary for correctness".
- **(B) Text splice + reparse.** **Viable.** Build IR → `emitText` → splice the continuation
  functions → reparse → `emitBinary`, with GC in the feature mask. No toolchain change. The cost is
  the one the file always named: text carries no DWARF, so async programs lose debug info and
  source maps.
- **(C) Separate runtime module.** **Proven, and preferred.** A hand-written `.wat` runtime owns
  the tag, `do_yield`, the context table and `spawn`/`step`; the guest imports them and contains
  **no stack-switching instruction at all**.

**Recommendation: (C).** It needs no compiler API, keeps the guest a plain module, leaves DWARF
untouched, and is already demonstrated — see §7.3.

### 7.3 What (C) proves

Three modules in one store (`abi ← guest ← coreloop`), each validated, then run on wasmtime 50:

1. **`cont.new` on an imported function works.** The coreloop imports `guest.main` and does
   `cont.new $ct (ref.func $main)`; `elem declare func $main` lives in the coreloop's own text.
2. **A guest suspends by calling an imported function.** The runtime exports `do_yield`, whose body
   is `(suspend $yield)`. The guest's main is `call $do_yield; i32.const 42`. Because that call runs
   on the guest's stack, the suspend suspends the *guest's* continuation. Parks, resumes, returns 42.
3. **`spawn` crosses the boundary as a funcref.** The guest produces `ref.func $worker` and passes it
   to `runtime.spawn`, which does `cont.new` on it and parks it in a runtime-owned table; a later
   `step` resumes it.

Fact 2 is why (C) works: the guest needs no continuation type, no `cont.new`, no `suspend` — only an
ordinary call to an imported function. `ref.func` is already emitted by the compiler
(`compiler.ts:11738`), so spawn needs no new capability either.

The costs (C) keeps: an async program is **two modules**, and the `.wat` runtime must ship and be
linked by whoever instantiates. The second is already how `tension::abi` is bound.

### 7.4 What would change this

If the compiler ever wants single-module async output with debug info, (A) is the path and the
writer is already correct. Nothing in the design depends on it: the tag vocabulary, the parking
rule and `__asyncPump` are identical across (A), (B) and (C).

## 8. Phases

Each phase is a round with its own gate. No phase starts before the previous one's tests pass.

- **P0 — the spike.** **Done 2026-11-18; see §7.** Mechanism (C) is proven end to end: a guest
  with no stack-switching instruction parks and resumes, `cont.new` on an imported function
  works, and `spawn` carries a `ref.func` across the module boundary. Also settled: Binaryen
  *can* emit a valid, runnable continuation module through the text path, but only with **GC in
  the feature mask** — without it the writer generalizes to `5d 70` and every engine refuses
  the module at parse. **No compiler integration in this round.**
- **P1 — the shell.** `__start` rewritten, coreloop emitted, `main` resumed, `$done`/`$idle`
  correct, `__asyncPump` exported. A program with one await that returns a value.
- **P2 — depth.** `main → a → b → await`, one capture. `try`/`catch` across an await.
  Loops with awaits. This is what Backend A cannot do, so it is the proof.
- **P3 — `spawn`.** Multiple continuations, a ready queue, `join` via await. Still
  host-free.
- **P4 — the host contract.** `rt.frame()` on the new machinery; park table integration;
  `take_early` still correct. `__asyncPump` replacing the three entries.
- **P5 — delete Backend A.** Only after P1–P4 pass Backend A's existing 78 checks unchanged.

**Backend A's suite is the specification.** Those 78 checks stay, and Backend B must pass
them unmodified. A backend that needs the tests edited is a backend that changed the contract.

## 9. Tests the footprint demands

Beyond Backend A's 78:

1. **A call runs nothing.** `let t = f(); assert(!ran);` — the body's first statement has not
   executed. Then `await t` and it has.
2. **Depth is one capture.** `main → a → b → await`: assert exactly one continuation exists
   at the park, not three.
3. **A no-await async function allocates nothing.** Compile a body with no await; the module
   contains no `cont.new` for it.
4. **`try`/`catch` across an await** unwinds correctly — the case Backend A cannot express.
5. **`spawn(f)` creates a stack; `spawn(f())` is a compile error.**
6. **Root cannot await.** `__coreloop` awaiting is a compile error (or unreachable, asserted).
7. **Nested pump refuses by name.**
8. **Two contexts interleave** — proven by a counter sequence, not by "it didn't hang".
9. **The host is called once per epoch**, not once per task.
10. **Byte-identical flag-off** on every existing fixture: a program with no async must emit
    exactly what it emits today.

## 10. Open questions

- **Who owns spawned contexts?** Sibling root per pool (simpler to reason about, one small
  stack each) or one shared coreloop across all of them (one scheduler, one policy). Deferred
  until P3.
- **What happens when `main` returns?** Proposal: the program ends, even if spawned work
  remains. Same rule as today, and it keeps lifetime legible.
- **Per-await mechanism selection.** With §5's contracts as *types* rather than an `i32`, the
  compiler could pick epoll vs frame vs waiters per site. That is the natural successor to
  this design and is not part of it.
- **Pool as a value.** `spawn(pool, f, a)` where a pool is a declared context budget, in the
  shape of `Scene.create(w, h, capacity)` and Zig's explicit allocator. Deferred until P3.
  Note the honest limit: wasmtime's stack knobs (`max_wasm_stack`, `async_stack_size`) are
  **per-engine, not per-continuation**, so a pool can enforce *count* but not *stack size*.
